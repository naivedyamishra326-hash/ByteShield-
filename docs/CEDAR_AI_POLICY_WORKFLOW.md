# ByteShield AI-Assisted Cedar Policy Engine & Copilot Workflow

## 1. Architectural Authority Contract

The integration of artificial intelligence into security policy authoring adheres to a strict architectural rule:

> **Core Principle:** AI models may help **author, explain, review, and simulate** candidate policies. However, **deterministic Cedar policy evaluation remains the sole authoritative engine** for runtime authorization decisions. Under no circumstances does the LLM directly authorize or bypass protected operations.

```
+-------------------------------------------------------------+
|                     AI Policy Copilot                       |
|   Natural language authoring, explanation & candidate test   |
+------------------------------+------------------------------+
                               | Candidate Policy
                               v
+-------------------------------------------------------------+
|                Cedar Validation Pipeline                     |
|  1. Syntax validation  2. Schema check  3. Test generation  |
+------------------------------+------------------------------+
                               | Validated Candidate
                               v
+-------------------------------------------------------------+
|              100-Scenario Impact Simulation                  |
|  Simulates candidate against catalogue; catches regressions|
+------------------------------+------------------------------+
                               | Impact Diff & Risk Score
                               v
+-------------------------------------------------------------+
|                  Authorized Human Review                     |
|   Security lead approves or rejects candidate in console    |
+------------------------------+------------------------------+
                               | Explicit Activation
                               v
+-------------------------------------------------------------+
|             Deterministic Cedar Policy Engine                |
|        Authoritative runtime authorization boundary         |
+-------------------------------------------------------------+
```

## 2. The 9-Stage Policy Lifecycle Pipeline

Every policy change passes through a deterministic 9-stage pipeline before taking effect:

1. **Natural Language Requirement:** Operator enters intent (e.g., *"Permit read_account for finance-agent on all active accounts"*).
2. **AI-Generated Candidate:** Copilot parses natural language constraints and synthesizes Cedar DSL syntax (`permit`, `forbid`, `principal`, `action`, `resource`, `context`).
3. **Syntax & Parse Validation:** The Cedar parser checks AST tokens, balanced braces, and reserved keywords. Invalid syntax is flagged with line numbers and prevented from proceeding.
4. **Schema Validation:** Verifies that declared actions, entities, and context attributes match the application's domain schema (`MCPSentinel::Action`, `MCPSentinel::Account`, `requestedAmount`, `resourceStatus`).
5. **Positive & Negative Unit Tests:** Generates automated test cases verifying that authorized scenarios evaluate to `ALLOW` and malicious out-of-scope scenarios evaluate to `DENY`.
6. **100-Scenario Simulation:** Simulates the candidate against the 100 adversarial attack catalogue to determine whether existing defenses are compromised.
7. **Simulation Impact Diffing:** Computes the exact delta:
   - Baseline passed vs Candidate passed
   - Security regressions (scenarios that previously passed but now fail)
   - Newly permitted operations
   - Newly blocked operations
   - Automated recommendation: `SAFE_TO_DEPLOY` vs `HIGH_RISK_REGRESSION` vs `CRITICAL_SECURITY_HOLE`
8. **Authorized Human Review:** Security operators inspect the impact diff in the Policy Studio UI before confirming.
9. **Explicit Policy Activation & Rollback:** The active policy version is atomically updated in the persistent store. Previous policy versions are retained in history, enabling immediate one-click rollback if operational issues arise.

## 3. Policy Copilot Capabilities

The `CedarCopilotService` (`src/services/cedarCopilot.ts`) exposes three core capabilities:

### A. Natural Language to Cedar Translation (`generateCandidatePolicy`)
Translates unstructured security requirements into structured Cedar DSL rules.
```cedar
// Auto-generated by Cedar Copilot for requirement:
// "Permit read_account for finance-agent on active accounts"
@id("copilot-permit-acc-read")
permit (
  principal == MCPSentinel::Agent::"spiffe://demo.local/agent/financial-remediation",
  action in [MCPSentinel::Action::"read_account", MCPSentinel::Action::"get_account_balance"],
  resource
)
when {
  resource.status == "active"
};
```

### B. Plain-English Policy Explanation (`explainPolicy`)
Explains complex Cedar rules in clear, non-technical English, breaking down the effect (`PERMIT` vs `FORBID`), target principals, actions, resource scopes, and context predicates.

### C. 100-Scenario Simulation Engine (`simulatePolicyImpact`)
Executes the candidate policy across all 100 adversarial scenarios in the catalogue without deploying to production.
- Detects if an overly permissive rule (e.g., `permit (principal, action, resource);`) permits direct prompt injections (`SEC-CAT01-001`) or excessive refund violations (`SEC-CAT04-003`).
- Returns structured impact objects with risk classifications.

## 4. Runtime Enforcement & Fail-Closed Guarantee

During active operation, all MCP tool proposals are evaluated by `defaultCedarPolicyEngine.evaluate()`:
- **Default-Deny:** If no explicit `permit` rule matches the principal, action, and resource, Cedar denies the request.
- **Forbid Precedence:** A `forbid` rule always overrides any matching `permit` rule.
- **Fail-Closed on Error:** If a policy parsing error or unhandled evaluation exception occurs, the system logs a security event and defaults to `DENY`, preventing unverified actions from executing.
